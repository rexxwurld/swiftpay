Security

Last updated: September 2026

This page describes the security practices actually built into SwiftPay's platform today. We'd rather this page be short and accurate than long and impressive - see the disclaimer at the bottom before drawing conclusions about compliance status.

Encryption in transit

All traffic to and from the API and dashboard is served over HTTPS/TLS. Secret API keys are never included in logs, error responses, or webhook payloads.

API key handling

  • Secret keys are stored as one-way hashes, never in plaintext.
  • Test and live keys/data are fully isolated from each other.
  • Keys can be rotated/regenerated at any time, and we track when a key was last used so you can tell if an old key is still active somewhere before revoking it.

Webhook security

  • Incoming bank webhooks are verified against a signature computed over the raw request body before anything is trusted or processed.
  • Outbound webhooks to your endpoint are signed with your webhook secret, so you can verify a delivery actually came from us.
  • Outbound webhook delivery is hardened against SSRF (server-side request forgery) - destination URLs are re-checked against private/internal IP ranges at send time, and redirects are never followed.

Financial data integrity

  • All money movement is recorded in a double-entry ledger, which is the system of record - wallet balances shown on the dashboard are derived from it, not the other way around.
  • Every financial state change (a payment settling, a payout completing, a refund processing) is written to an audit log with an actor, an action, and a timestamp.
  • Ambiguous outcomes from our banking provider (a timeout, a 5xx, a dropped connection) are never treated as a safe default in either direction - they're held for reconciliation rather than guessed at.

Access controls

  • Rate limiting is applied per category of endpoint (payments, payouts, withdrawals, account resolution, admin actions each have their own limits) rather than one shared limit for everything.
  • Administrative actions that move money or change account state require a named admin session with a specific role, not just a shared operator credential.
  • Merchants can only ever see and act on their own data - cross-merchant access is checked on every lookup, not assumed from routing alone.

Reporting a vulnerability

If you believe you've found a security issue, please email security@swiftpay.io with details. We ask that you not publicly disclose an issue until we've had a reasonable chance to address it.

What this page is not

This page describes the software's technical security practices. It is not a compliance certification of any kind (PCI DSS, SOC 2, ISO 27001, or otherwise), and none should be inferred from it. SwiftPay does not currently hold, and does not claim to hold, any third-party security or compliance certification. Software passing internal testing is a separate thing from a business being licensed, audited, and legally authorized to operate payment infrastructure - if that matters to your decision to integrate, please ask us directly about our current regulatory and compliance status rather than assuming it from this page.
